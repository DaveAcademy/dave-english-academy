# Ranking System

Class ranking (points-based, academy-wide feature) vs. game ranking (Game Center leaderboards) are **separate systems** sharing only the `rank()` window-function convention. This doc covers class ranking in depth; see `GAMING-SYSTEM.md` §9 for game-specific leaderboards.

## 1. Class ranking — source of truth

`point_transactions` (append-only ledger, `0019`) is the single record of every point ever awarded. `students.points` is a trigger-maintained cache (`refresh_student_points_cache()`), not directly editable — the `UPDATE` grant on that column is revoked academy-wide, admins included. The only way to change a student's total is inserting a ledger row. See `DATABASE.md` §3 for the RLS mechanics.

**Standing rule: never write to `point_transactions`/rankings directly outside the existing award UI/RPCs.** Dave manages all point changes personally.

## 2. Ranking Model V3 (current, confirmed-live)

**Authoritative description:** the teacher gives each student one total Class Score for that class. The system records it against the correct student, level, date, and class, then calculates Weekly and Monthly rankings automatically. **Homework, PDF preparation, games, participation, bonuses, and penalties are not separate Class Score components** — an earlier design that composed Class Score from those individual categories was investigated (`ranking-model-v3-investigation-2026-08-18.md`, historical record only) and explicitly **rejected**. Migration `0163` briefly added schema for that rejected per-category approach (a `prep` point category, a `homework_status.points_awarded` claim-guard column); the schema is applied in production but the application code that would have written through it (a `prep`/`homework` award path in `Rankings.jsx`/`storageBridge.js`) was never shipped — `0167` (below) also excludes those categories from every ranking total, so the leftover schema is inert. Do not resurrect this without a fresh product decision from Dave.

**How Class Score actually works** (`Rankings.jsx` "Class Score" section, `class_session`/`class_session_id`, migrations `0137`-`0139`, `0164`-`0167`): the teacher never opens, picks a date for, or manages a session — entering a Class Score for the first student in a level/group on a given day lazily finds-or-creates *today's* session for that group; every other student's score that day attaches to the same session. `class_score` is its own `point_categories` key (`0165`); a partial `UNIQUE(student_id, class_session_id)` index scoped to `category_key = 'class_score'` (`0164`, `0166`) rejects a second score for the same student+session at the DB level. `get_class_leaderboard()`/`get_weekly_class_leaderboard()`/`get_monthly_class_leaderboard()` (`0139`, restricted to `category_key = 'class_score'` by `0167`) are the sole source for the Class/Week/Month leaderboard tabs — no other category contributes to these totals, even if a session happens to be open when it's recorded.

**Separately, an "Add Points" ad-hoc path still exists** (`Rankings.jsx` "Add Points" section → `awardPoints()`/`bulkAwardPoints()` in `storageBridge.js` → INSERT into `point_transactions`, `category_key` `bonus`/`penalty`) for quick, session-less point adjustments outside a specific class. This path is unchanged by Ranking V3 and still feeds the **All-Time** leaderboard tab (`get_group_leaderboard()`, unfiltered by category — sums every category including `class_score`, `bonus`, `penalty`), but does **not** feed Class/Week/Month. Attendance, homework, and exams still **do not** feed the ledger at all — deliberately removed (`0008`) because the old automatic formula produced flat zeros for most students; those pages still function independently.

**Duplicate-award protection (`0162`, applied to prod 2026-08-18):** the manual award path (`category_key in ('bonus','penalty')`) previously had only a client-side, per-tab, non-persistent dedupe check (`Rankings.jsx` `DUP_WINDOW_MS`) — not a theoretical gap: `0097` reversed a real production double-submission incident. A `BEFORE INSERT` trigger (`prevent_duplicate_point_transaction`) now rejects an insert when an identical, non-reversal, non-baseline row (same student/category_key/points/reason/awarded_by) was written in the last 120 seconds — the same window the client already enforces, so no UX change for legitimate use. Homework/exam/achievement/game/lesson-work awards use different `category_key` values and are untouched; games and lesson-work already have their own idempotency (`0141` round tokens; `points_awarded IS NULL` claim guard).

## 3. Class ranking vs. game ranking — explicit distinction

| | Class ranking | Game ranking |
|---|---|---|
| Source | `point_transactions` ledger | `game_sessions` / `game_level_progress` |
| Scope | Level-scoped (A/A1/B/C), week/month/all-time | Per-game, per-student |
| Write path | Manual: Class Score (one number/student/class, session auto-resolved) for Class/Week/Month; separate ad-hoc "Add Points" for All-Time only — see §2 | `submit_game_round()`, fully automatic, server-graded |
| Currency | "Class Points" | Game score (flat per-correct); "Game Points" as a separate currency is **planned, not implemented** — see `GAMING-SYSTEM.md` §12 |
| Never auto-feeds | Games do not write `point_transactions` at all (by design — the strongest mitigation against self-awarded points) | N/A |

## 4. Personal records / Top 5 / ties

- Class leaderboards use `rank()` (not `row_number()`) in every RPC — genuinely tied students share a rank number, next rank skips accordingly. This is correct in every RPC that was ever audited.
- **known-issue-fixed / known-issue-open, UI-level (mixed):** rank display was historically inconsistent across the app even though the underlying SQL was always correct — several surfaces rendered array index instead of `row.rank`. Status per surface, from the 2026-07 ranking audit and subsequent Ranking V2 work:
  - Rankings.jsx Level Leaderboard, class-by-class grid, PortalHome hero — always correct (`row.rank`).
  - Rankings.jsx main "top" table (pooled-all-levels, array-index rank) — **known-issue-open at audit time**, Ranking V2 plan calls for deleting this table entirely in favor of the Level Leaderboard; verify current code before assuming still open.
  - MyRanking.jsx medal color — **known-issue-fixed** (Ranking V2 plan item: `medal(i)` → `medal(row.rank - 1)`); Game Center's equivalent bug (`d5ca5a2`) is **known-issue-fixed** separately.
- Recognition (Student of the Week/Month) tie-break: **known-issue-fixed** (`0153_fix_recognition_tie_break.sql`, applied to production 2026-08-17). `finalize_recognition()` (0023) has the correct tie chain but was never swap-compatible with the Recognition page's admin-choose-a-candidate workflow — it has no `student_id` parameter, issues no certificate, and returns a different shape. Rather than reroute the page to it, `finalize_recognition_winner()` (the function actually wired to `Recognition.jsx`) was extended in place: it keeps its exact interface, admin-selection semantics, and certificate issuance, and adds the same rank()-based tie detection (points desc, active_days desc, attendance rate desc) as `finalize_recognition()`. When the admin's chosen student is genuinely tied for rank 1, every tied student is recognized as a co-winner (own award row + own certificate); otherwise behavior is unchanged from before. Verification: the added tie-detection SQL was checked against literal synthetic data for clear-winner/2-way/3-way/lower-rank-tie cases (all correct) and the deployed function body was confirmed live in production (`prosrc` contains the new logic). Full RPC end-to-end and UI verification were **not** performed — the environment blocked all test writes to `students`/`point_transactions`, even inside rolled-back transactions, in two separate sessions. No isolated non-production Supabase project, local Docker-backed Supabase stack, or documented fixture/seed mechanism exists in this repo (checked 2026-08-17: only branch on the prod project is `main` itself; `supabase/config.toml` is absent; Docker is installed but not running) — a disposable Supabase preview branch remains the only path to true RPC execution and would need Dave's cost approval before creating one. Static UI-contract review (2026-08-17): `Recognition.jsx` calls `finalizeRecognitionWinner()` but never consumes its return value (`storageBridge.js:344`) — it re-fetches `recognition_awards` (including `is_co_winner`) afterward — so `0153`'s new multi-row RPC return (one row per co-winner, vs. the old always-one-row shape) cannot break the caller. `is_co_winner` is already correctly read and displayed (`portal:coWinnerLabel`) in the student portal's `MyRanking.jsx:190`. This de-risks the UI side of the remaining gap but is not a substitute for executing the RPC.

## 5. Rank calculation — key RPCs

- `get_group_leaderboard(level, period_type, period_start)` — main engine, used by Rankings, MyRanking, PortalHome, Recognition candidates.
- `get_student_ranking_summary(student_id)` — one student's lifetime/week/month points + ranks.
- `finalize_recognition_winner(...)` — recomputes the period total server-side from the ledger, never trusts a client-supplied value.

`all_time` scope was historically inconsistent (ranked off the cross-level cache while week/month joined on snapshot level) — fixed per the Ranking V2 plan (`0029`-era) to rank off `sum(point_transactions.points) where pt.level = p_level`, same pattern as week/month. **known-issue-fixed** — verify against current `get_group_leaderboard` body if a new session needs certainty.

## 6. Class Session architecture (Ranking V2 Phase 4 → Ranking V3) — status: live

Schema (`class_group`, `class_session`, `point_transactions.class_session_id`) and RPCs (`get_class_leaderboard`, `get_weekly_class_leaderboard`, `get_monthly_class_leaderboard`) shipped as migrations `0137`-`0139`; Class/Week/Month tabs now run on them, restricted to `category_key = 'class_score'` (`0167`) — see §2.

**History:** Week/Month were first wired to these RPCs before any session-opening workflow existed in real day-to-day operation (every historical row had `class_session_id = NULL`, so the RPCs returned 0 for every student) and were reverted back to `get_group_leaderboard()`. Ranking V3 (2026-08-18) resolved this by removing the manual "open a session" step entirely — a session is now lazily found-or-created the moment a teacher enters the first Class Score for a level/group on a given day (see §2) — and re-wiring Class/Week/Month to the session-based RPCs. Historical (pre-V3) `point_transactions` rows keep `class_session_id = NULL` permanently — there is no safe way to retroactively assign a session to a row from before sessions existed as a modeled entity — and are excluded from Class/Week/Month, fully counted in All-Time.

Historical (pre-V2) manual point rows are **never** backfilled with a `class_session_id` — there is no safe way to retroactively assign a group to a row from before groups existed as a modeled entity. They remain fully counted in lifetime totals, excluded from Class/Weekly/Monthly session views, with the UI stating why.

## 7. Known architectural concerns

- **Level-snapshot gap (open):** `game_sessions` has no *academy*-level snapshot at play time, which affects the existing score ranking's level/group scoping for any student who changes academy level mid-history. This is explicitly a **different** "level" concept from Game Level Progression (see `GAMING-SYSTEM.md` §7c) — both remain open, distinct items; do not silently bundle a fix for one into work on the other.
- **Recognition/leaderboard inconsistency for promoted students:** `finalize_recognition_winner` filters by level while the general leaderboard doesn't cleanly handle cross-level history the same way — flagged, not reconciled.
- **No bounds check on award magnitude** — see `DATABASE.md` §7.
- **No admin-facing reversal/undo UI beyond a session-local, own-last-award-only undo** — bulk/historical correction still requires manual re-entry.
- **Student 9, 2026-08-12 penalty cluster — investigated 2026-08-18, evidence leans legitimate, not corrected:** four (not three) `-1` penalty rows exist for student 9 within ~3 minutes, ids 1158 (08:18:27), 1162 (08:18:49, +22s), 1163 (08:21:01, +132s), 1164 (08:21:33, +32s), all `awarded_by` the same teacher. Row-by-row this does **not** match the `0097` signature (an exact resubmission of an identical multi-student batch): 1158 was one row of a genuine 5-student mixed-points batch (`students 9,15,16,17,30`, points `-5,-2,-1,2` — a real "Award Class Points" submission); 1162 and 1163 were each separate single-student-only "Bulk class points via Rankings" batches (batch composition `{9:-1}` only, not a repeat of the 5-student batch); 1164 has `reason = NULL`, meaning it came from the *different* "Add Points" quick-award path, not the bulk form at all. The client-side `DUP_WINDOW_MS` bulk-resubmit guard in `Rankings.jsx` keys off the full batch composition, so it would not have flagged 1162/1163 as duplicates of 1158 (different student set). The server-side `0162` guard (shipped same day as this investigation, 2026-08-18) would have blocked 1158→1162 (22s apart, matching student/category/points/reason/awarder, within 120s) but **not** 1162→1163 (132s, outside the 120s window) or 1163→1164 (different `reason`, so the match predicate never fires). Conclusion: the ledger evidence is consistent with the teacher deliberately re-opening the award panel to add further `-1` penalties for this one student over ~3 minutes (a materially different shape from 0097's single-click-resubmitted-identical-batch), but the ledger alone cannot prove classroom intent with certainty. **Not corrected**: no reversal was written, per the standing no-points-writes rule; pending Dave's decision on whether any of the four rows should be reversed.
