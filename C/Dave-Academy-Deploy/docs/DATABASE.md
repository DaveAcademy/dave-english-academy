# Database

Supabase/Postgres. See `ARCHITECTURE.md` for how RLS/RPCs fit the overall system. This doc covers schema, migration conventions, and DB-specific production rules.

## 1. Migration numbering & conventions (confirmed-current)

- Sequential numbered files: `0001_schema.sql` ... `0151_game_level_leaderboard.sql` — **151 numbered files, current head**.
- **`PROD_RECONCILED_*` files** are a separate, deliberate category: corrective/reconciliation migrations documenting schema that was applied directly to production (via MCP `apply_migration`, not `supabase db push`) in an earlier session and never captured as a numbered local file. They are `create table if not exists` / `create or replace function` guarded so re-applying is a no-op. Six such files exist at doc time. `PROD_RECONCILED_achievement_engine_schema.sql` (an untracked, superseded duplicate of the same tables) is one of them, but the achievement-engine schema itself is now captured properly as numbered migrations `0105_achievement_engine_schema.sql`–`0110` (committed `4fe705b`, applied to the prod ledger as `20260810055447_0105_achievement_core_schema` onward) — see §7. See `docs/migration-reconciliation-2026-08-15.md` for the methodology.
- **Never rewrite an already-applied migration file.** If prod needs a schema correction, write a new numbered (or `PROD_RECONCILED_`) migration — do not edit history in place. This rule exists because of at least one documented incident where an unrecorded-ledger migration would have been silently re-run and regressed a live function (`docs/migration-ledger-and-rls-repair-plan.md` §2, "the `db push` footgun").
- **Ledger/production parity has diverged more than once historically** (documented repair passes: 2026-07-25 for 0024-0028, 2026-08-15 for the payment/ranking/gaming range). **known-issue-open (latent, not currently blocking):** local migration files 0029+ have at points been untracked in the prod ledger per prior-session notes; do not run `supabase db push` in a fresh session without first re-confirming ledger/production parity for the affected range using `supabase migration list --linked`.

## 3. RLS principles (confirmed-current)

- **Ledger tables (`point_transactions`, `payment_transactions`) are append-only by construction:** RLS grants SELECT + INSERT only, no UPDATE/DELETE policy for any role — Postgres rejects those verbs outright regardless of role. Corrections happen via a new reversal row (`is_reversal`/`reversed_transaction_id` columns), never by editing history.
- **`point_transactions` has a `BEFORE INSERT` duplicate-award guard (`0162`)** in addition to the append-only RLS: `prevent_duplicate_point_transaction()` rejects a manual award insert (`category_key in ('bonus','penalty')`) that exactly matches student/points/reason/awarded_by of a non-reversal row inserted in the last 120 seconds. Scoped to manual awards only — other `category_key` values (homework/exam/achievement/game/lesson-work) are unaffected and have their own protections. See `RANKING-SYSTEM.md` §2.
- **`students.points` is not client-writable.** Column-level `UPDATE` grant on `students` is revoked academy-wide and re-granted per-column, excluding `points`/`id`/`created_at`. The only path to change it is inserting a `point_transactions` row, which a trigger (`refresh_student_points_cache`) then sums into the cache.
- **Teacher scoping:** `is_teacher()` alone (role-only, no level/group scope) was the pattern on ~15 tables until the 2026-08-14 remediation (migrations 0131-0136) added level-based scoping via `teacher_group_assignments` to the 6 highest-sensitivity tables (exam_scores, homework, lesson_work, student_lesson_progress, attendance, certificates). `curriculum_progress`'s UPDATE policy is scoped the same way as of `0156_curriculum_progress_teacher_level_scope.sql` (2026-08-17) — its `level` column is a direct match against `teacher_group_assignments.level`, no join needed; SELECT stays open (`using (true)`), unchanged. **Applied to production 2026-08-17** (migration `20260817153027_0156_curriculum_progress_teacher_level_scope`); `pg_policies` confirmed the UPDATE `qual`/`with_check` now require the `teacher_group_assignments` match for teachers while admin stays unrestricted and SELECT is untouched. Real teacher write behavior not runtime-tested (no safe test path this session). **known-issue-open (latent):** `files` has no level column at all (it's a general admin/teacher resource library — lesson PDFs, cert templates, general media — not tied to a level or student), so it can't be scoped by mirroring this pattern; giving it a level dimension would be a product decision (should shared resources even be level-restricted?), not a mechanical fix. Real exposure on both remains low (only 2 teachers exist, both all-level, at the time of the audit).
- **Student self-read** uses `is_own_student(student_id)`, a SECURITY DEFINER helper, rather than a raw `profile_id` subquery — this was itself the subject of an RLS hardening pass (`0024`/`0028`, see `docs/migration-ledger-and-rls-repair-plan.md`) after a documented over-broad column grant on `students.profile_id` was found and closed.
- **Points/achievements RLS was already correctly level/group-scoped** even before the 2026-08-14 remediation — not part of that gap.

## 5. Production DB rules (standing)

1. **Never write to `point_transactions` or `students.points`/rankings directly** — Dave manages all point changes personally through existing UI/RPCs. This applies to Claude sessions and to any tooling with prod write access.
2. **Never rewrite an already-applied migration** — see §1.
3. **Runtime verification required** before claiming a DB-affecting change is correct in production — static SQL/migration review has produced false-positive "verified" claims at least twice in gaming-system work (an adaptive-difficulty tier-scale bug and an unlocked-lesson join bug, both caught only by live testing — see `GAMING-SYSTEM.md`).
4. **Do not run `supabase db push`** without first confirming ledger/production parity (`supabase migration list --linked`) for the full range being pushed.
5. Corrective migrations for confirmed prod drift use the `PROD_RECONCILED_*` naming convention (see §1), not edits to the original file.

- ~~Achievement-engine schema had no numbered local migration~~ — **resolved**: `0105_achievement_engine_schema.sql`–`0110` (committed `4fe705b`) reconstruct `achievement_definitions`/`student_achievements`/`student_metric_snapshots` plus `bump_student_metric`/`evaluate_achievements`, and are confirmed applied in the prod migration ledger (`20260810055447` onward). The untracked `PROD_RECONCILED_achievement_engine_schema.sql` is now a redundant (harmless, idempotent) duplicate of a subset of 0105 and can be deleted whenever convenient — not required.
- ~~`get_leaderboard()` (from `0008`) remains defined and `GRANT`ed~~ — **FIXED**: `0128_drop_dead_get_leaderboard.sql` dropped it; confirmed applied in prod migration ledger (`20260814130512`) and confirmed absent from `pg_proc` in production (2026-08-17). Zero frontend callers existed at drop time; all leaderboard reads go through the level-scoped `get_group_leaderboard()` (0023).
- ~~No CHECK constraint on `point_transactions.points` magnitude~~ — **FIXED 2026-08-17**: `0154_point_transactions_magnitude_check.sql` added `CHECK (points BETWEEN -1000 AND 1000)`, applied to production. Range covers full observed history (non-baseline rows -211..236, one-time `baseline_migration` rows 105..608) with headroom; 0 of 1539 existing rows violated it. Constraint existence and existing-data validity verified live; insert/rejection behavior not runtime-tested (blocked by the no-points-writes rule in §5.1) — a typo like `500` for `5` is still not caught unless it also breaches ±1000.
- Reversal mechanism (`is_reversal`/`reversed_transaction_id` on `point_transactions`) exists in schema but is only exercised via the session-local undo added in Ranking V2 Phase 2 — bulk/admin-side reversal UI is still **planned**, not built.
- ~~8 functions with mutable `search_path`~~ — **FIXED 2026-08-17**: found via Supabase's own `get_advisors(type: "security")` lint ("Function Search Path Mutable", WARN) on `game_level_to_length_cap`, `game_level_to_tier`, `game_tier_bonus`, `month_bounds`, `week_bounds`, `get_activity_feed`, `get_monthly_payment_collection`, `get_payment_collection_summary`. None are `SECURITY DEFINER` (all run as invoker), but an unpinned `search_path` still lets a caller-controlled `search_path` shadow the unqualified `is_admin()` call inside the three admin-report functions with an object from another schema. `0157_function_search_path_hardening.sql` pins `search_path = public, pg_temp` on all 8 (all 8 bodies already schema-qualify their own table refs with `public.`, so this was a pure hardening no-op for current behavior) — applied to production and confirmed in the migration ledger (`20260817170408`); `pg_proc.proconfig` verified non-null on all 8 post-apply.
- ~~`finalize_recognition()` (the tie-break-correct recognition function) is dead code — the page calls `finalize_recognition_winner()` instead, which has no tie-break and forces `is_co_winner = false`~~ — **STALE, superseded 2026-08-17**: `0153_fix_recognition_tie_break.sql` (applied to production) redefined `finalize_recognition_winner()` itself to detect ties and set `is_co_winner` correctly — this entry described the pre-`0153` state and was never updated when that migration landed. `finalize_recognition()` (`0023`) remains separately dead/unused, which is a harmless naming leftover, not a bug. See `RANKING-SYSTEM.md` for current status.

- **`bump_student_metric(student_id, metric_key, delta)` had no caller-authorization check and was directly callable by `anon`/`authenticated`** — **FIXED 2026-08-17**: found via a fresh `get_advisors(type: "security")` pass (`anon_security_definer_function_executable` / `authenticated_security_definer_function_executable` on 56/59 functions respectively — most of those are false-positive-shaped, each already gated internally by `is_admin()`/`auth.uid()`/caller checks, e.g. `claim_first_admin`, `resync_sequences`, `revoke_recognition_award`, `get_student_login_info`, all confirmed by reading their bodies). `bump_student_metric` was the one genuine gap: unlike `evaluate_achievements` (hardened in `0126b_secure_achievement_evaluator.sql` with a checked-wrapper/unchecked-internal-worker split), `bump_student_metric` had zero authorization logic and unconditionally upserted `student_metric_snapshots` for any `student_id`/`metric_key`/`delta` passed in — reachable directly via `/rest/v1/rpc/bump_student_metric` by an unauthenticated caller. Grep confirmed zero frontend callers (`src/` has none); the only real call sites are `on_attendance_evaluate_achievements`, `on_lesson_progress_evaluate_achievements`, `on_lesson_work_submission_evaluate_achievements`, and `submit_game_round` — all `SECURITY DEFINER`, all owned by `postgres` (same owner as `bump_student_metric`). Since there is no legitimate direct caller at all (unlike `evaluate_achievements`, which a student's own session does call directly), the fix was a straight `REVOKE ALL ... FROM public, anon, authenticated` (`0158_revoke_bump_student_metric_direct_access.sql`), not a wrapper split — matching the treatment already given to `_evaluate_achievements_internal`. Applied to production (`20260817171541`); `has_function_privilege` confirmed `anon`/`authenticated` now `false`, `postgres` (the owner, and the role every internal caller runs as) still `true` — internal call sites are unaffected by construction, not just by assumption. This closes a real, previously-undocumented data-integrity gap on the metrics table `evaluate_achievements()`'s qualification checks read from, independent of the separately-paused achievement→points bonus gate.
- **`public.app_setup_status` — RLS enabled, no policy** — **investigated 2026-08-17, confirmed intentional, no action taken**: a one-row singleton (`id=true, first_admin_created=true`, already completed 2026-07-09) tracking whether the one-time first-admin bootstrap has run. `0002_setup_bootstrap.sql`'s own comment states no RLS policy is defined on the table itself by design — all access goes through `SECURITY DEFINER` functions (`is_setup_complete()`, `claim_first_admin()`, both confirmed self-checked, e.g. `claim_first_admin()` requires `auth.uid()` non-null and row-locks the singleton). RLS-enabled-with-no-policy is Postgres's default-deny posture: it blocks *all* direct table access from every role, which is exactly the intended effect here, not an oversight. No policy was added.
- **`attendance`/`payments` each carried two byte-identical unique btree indexes on the same columns** — found via a fresh `get_advisors(type: "performance")` pass (`duplicate_index`, WARN), 2026-08-17. `attendance_student_id_date_key` duplicated `attendance_student_date_unique` (both `unique (student_id, date)`); `payments_student_id_year_month_key` duplicated `payments_student_period_unique` (both `unique (student_id, year, month)`). The `_key`-suffixed pair (Postgres's default auto-generated constraint name) is absent from `0001_schema.sql` and every other numbered migration or app-code reference (grepped both the repo and the deploy worktree) — only the `_unique`-suffixed pair, added explicitly in `0001_schema.sql` via an idempotent `do $$ ... exception when duplicate_object then null; end $$` block, is documented anywhere; the `_key` pair's origin is an earlier undocumented direct schema change (consistent with the `PROD_RECONCILED_*` pattern elsewhere in this doc). Confirmed via `pg_constraint` that both are plain `UNIQUE` constraints, not FK targets, so dropping one has no cascading effect. Pure write/storage overhead, zero functional or security impact — a mechanical, no-product-decision fix. `0159_drop_duplicate_indexes.sql` drops the undocumented `_key` pair — **APPLIED to production 2026-08-17** (ledger version `20260817174708`); confirmed live via `pg_indexes`/`pg_constraint`: `attendance_student_id_date_key` and `payments_student_id_year_month_key` are gone, `attendance_student_date_unique` and `payments_student_period_unique` remain as the sole unique constraints on their respective column sets, no other indexes on either table changed.
- **Performance advisor, investigated but not actionable this session:** `multiple_permissive_policies` (528 WARN rows) and `auth_rls_initplan` (36 WARN rows) are real per-Supabase's-own-linter findings, but at current scale (37 active students, small per-table row counts throughout) their runtime cost is negligible; fixing either properly means auditing and consolidating RLS policies table-by-table, which is a large, security-sensitive refactor, not a one-migration mechanical fix — deliberately not attempted this session. `unindexed_foreign_keys` (37 INFO rows) and the remaining 2 `unused_index` entries (`messages_scope_idx`, `messages_context_idx`, `files_category_idx`) are low-priority housekeeping at this data volume, also deferred.

- **`can_read_lesson_pdf()` / `student_unlocked_lesson_number()` — completion-chaining unlock loophole closed (`0160`, 2026-08-18):** both functions previously OR'd in "student completed lesson N-1" as a way to unlock lesson N, alongside the level cap (`max_available_lesson`) and the teacher's schedule pace (`current_lesson_number`). That clause let a student who finished a lesson open the next one immediately, regardless of whether the class had actually reached it — confirmed exploited by real students (see `CURRICULUM.md` §5 for the exact rows). `0160` drops that clause from both functions; unlock is now purely level-cap AND schedule-pace. Applied to production (`20260818084746`), confirmed via `pg_get_functiondef` and runtime-verified via `set local role authenticated; set local request.jwt.claims` impersonation against 4 real students (one per level: A id 38, A1 id 35, B id 19, C id 1) — schedule-boundary lock, level-cap lock, previously-accessible lessons staying open, and rejection of a direct `can_read_lesson_pdf(<manipulated lesson id>)` call were all confirmed at the SQL layer. Teacher/admin access unaffected by construction — every RLS policy that calls these functions (e.g. `attachments_read`, `0033`) already ORs in `is_admin()`/`is_teacher()` ahead of them, and neither function resolves a caller who has no `students` row.
- **`curriculum_progress.max_available_lesson` (Level A) lowered 20→15 (`0161`, 2026-08-18):** data-only change, no function definitions touched. Dave's final permanent-ceiling targets (A=15/A1=10/B=40/C=50) matched production exactly for A1/B/C already; only Level A's cap moved. Safety-checked against real `student_lesson_progress` completion history before applying (highest legitimate completion per level: A=14, A1=5, B=40, C=50 — all within target) and runtime-verified via impersonation of student id 38 (Level A, pace 14): lesson 14 opens, lesson 15 stays pace-gated (`0160` behavior, unchanged), lesson 16+ now ceiling-gated (new). See `CURRICULUM.md` §5.
